# 逐層架構圖（從程式碼實際依賴畫出）

用在：使用者要「畫架構圖」「整理分層」「看某一層現在長怎樣」「從頭一層一層畫」「展開模組內部」。
目標不是畫理想架構，而是**把程式碼現在真實的呼叫關係畫出來**，讓違規、重複、孤兒、循環一眼可見，再把問題列成待辦清單。

---

## 0. 心態與底線

- **不要先假定既有分層正確**。先看入口與實際呼叫，再決定每層放什麼。
- **每一條線、每一個檔名都要有 grep 證據**。沒查過的不畫；畫錯比不畫糟。
- **一次只畫一層**，畫完給使用者看、確認後再往下一層。不要一次產出整張大圖（使用者會覺得「很糟」並要求重畫）。
- **範圍要完整**：展開「模組內部」時，每個模組都要處理；沒有內部結構的（單檔、或檔案之間互不引用）集中放進一張「沒有內部結構的模組」卡片，不要只挑兩三個展開（使用者會問「其他模組沒有內部？」）。
- **只讀程式碼，不改程式碼**。發現的問題寫進待辦清單，修改交給負責改 code 的人／agent。
- 外部動作（push、PR、commit 到 repo）一律要使用者明確授權。產出放在 repo 內「不進 git」的資料夾（例如 `Claude outputs/`）。
- 被使用者指出錯誤時：直接承認哪裡錯、為什麼錯，修圖，並同步修正待辦清單裡相關描述。
- 使用者說「你自己去看」時：自己開頁面截圖（含放大截圖）找問題，不要只跑數字檢查就說沒問題。

## 1. 層的定義（預設，可依專案調整）

| 層 | 名稱 | 放什麼 | 判斷依據 |
|---|---|---|---|
| L0 | 入口（Entry） | 使用者從哪裡進來（右鍵選單、開始功能表、檔案關聯、終端機）→ 第一個碰到的執行檔 → 執行檔間怎麼轉交 | manifest（AppxManifest 等）、各執行檔的 Main/Startup |
| L1 | 畫面（Presentation） | 上排：Renderer（實際畫面，含「無畫面」模式）；中排：共用畫面狀態（Controller）；下排：資料／目錄（不持有狀態的清單、描述器）；旁邊：只給某個 renderer 用的版面表 | 畫面類別、`*PresentationController`、版面計算檔 |
| L2 | 應用（Application） | 上排：應用服務／查詢／指令（每一欄對齊上方 L1 呼叫它的那張卡片）；左下：用例（共用基底＋各模組用例）；右下：任務生命週期等橫切服務；最底：往 L3 的出口 stub | `*/Application/`、`*Service`／`*Queries`／`*Commands`／`*UseCase` |
| L3 | 處理器／儲存／基礎設施 | 各模組處理器、共用處理、儲存、外部引擎包裝、橫切（在地化、字型、診斷、繪圖、根目錄零散檔、設定模型）；**外部依賴**（NuGet 套件含版本、作業系統元件、外部程式、網路下載）放在使用它的方塊正下方 | 由 L2 往下 grep；套件版本看 csproj |
| L4 | 模組內部 | 每個 L3 模組一張面板：模組內「檔案 → 檔案」的型別引用圖；檔案太多的模組（如翻譯）改畫資料夾層級，另開一張面板畫子模組 | 對每個模組資料夾掃型別定義與引用（見 §2.9） |

注意：「入口」不是「路口」；L0 只畫入口與執行檔，畫面之後的事屬於 L1。

## 2. 調查流程（每一層都照做）

1. **列出這層的候選節點**：`find` 該層資料夾、`grep -hn "^(public|internal) .*(class|interface|record|enum)"` 取型別清單與行數。
2. **一次 grep 建索引**（檔案系統慢時尤其重要，避免逐型別 grep 逾時）：
   ```bash
   grep -rowE --include=*.cs "TypeA|TypeB|TypeC|..." src/ProjA src/ProjB ... | sort -u > /tmp/refs.txt
   grep -v /obj/ /tmp/refs.txt | grep -v "<該層自己的資料夾>" \
     | awk -F: '{a[$2]=a[$2]" "$1} END{for(k in a) print "## "k":"a[k]}' | sort
   ```
   得到「每個型別被哪些檔案用」。
3. **確認是真呼叫還是註解**：命中後一定再 `grep -n` 看那一行。`<see cref="..."/>` 只是 XML 註解，**不算呼叫**（曾因此誤把三個 renderer 畫成跳層）。
4. **找跳層**：上層檔案直接引用下下層（例如 Presentation 直接用 `*Processor`、`ClickraStorage`、`*Settings` 儲存類別）。用一條 regex 掃上層所有資料夾。
5. **找每個節點的上游與下游**：
   - 上游＝誰呼叫它（含非上一層的呼叫者：CLI、Startup、Shell、renderer）。
   - 下游＝它呼叫誰／資料從哪來。**「不呼叫下一層」≠「沒有下游」**：純資料表的包裝類別，下游就是那份資料來源檔（例：`ConvertCommandRegistry` → `src/Shared/ConvertCommandMetadata.cs`），要畫出來。
6. **查方法層級**（使用者問「它用來幹嘛」時）：`grep -rnoE "TypeName\.[A-Za-z]+"` 統計每個呼叫者用了哪些成員，整理成「誰用／用來做什麼」表。
7. **查是否有測試保證**（兩份清單是否一致等）：grep tests。
8. 記下每條關係的檔案與行號，之後寫進圖與待辦清單。
9. **L4 資料**：在使用者電腦上跑一支腳本（不要把整個 repo 搬到雲端）：對每個模組資料夾，取出每檔定義的型別，再找模組內其他檔是否以單字邊界引用這些型別（去掉註解與字串後比對），輸出 `{module: {nodes: {file: {lines, files}}, edges: [[a,b],...]}}` 的 JSON。partial class 多個檔合成一個節點（如 `ClickraStorage.*.cs`）。同時記錄每個模組引用了哪些「其他模組」，寫在面板頁尾。

## 3. 版面規範

### 3.1 整體
- 每層是一個區塊：**左側標題欄**（大字「L0/L1/…」用層色、下方粗體中文名、再下灰色英文名），區塊用**淡底色＋左側一條細色線**，不要整圈粗外框、不要直書色帶（使用者覺得醜）。
- 由上往下讀；層內再分「band」小標（如「使用者動作」「門（執行檔）」「畫面（Renderer）」「共用畫面狀態」「資料／目錄」「應用服務」「轉換用例」「往下 → L3」）。
- 圖寬固定（約 1480＋左側標題欄 76），**不能有右側欄**擠壓圖面。

### 3.2 方塊內容：檔名直接寫出來
- **不要用 hover tooltip 顯示檔名，也不要用 `<title>`**（使用者明確拒絕；也不要做右側檔案清單面板）。
- 方塊結構：粗體標題 → 1~3 行角色說明 → 細分隔線 → 灰色小字資料夾路徑 → 深色等寬字檔名。
- **檔名一律寫完整副檔名（`.cs`）**，不要有些省略有些沒有（使用者會問）。
- 檔名太多時：
  - 共同前綴寫一次，下面列後綴，並標明「`DashboardWindow.*.cs（18 檔）`」。
  - 多欄排列，**欄優先（由上往下再換欄）**，讓同類（Events.*、Paint.*）排在一起。
  - 名稱太長換行時**優先在後綴詞切開**（`ConversionUseCase-` / `Registry.cs`），不要在單字中間斷。
- **同一排的方塊等高**，高度取最長清單；用 assert 檢查文字不超出方塊。
- 「也被：…」一行列出非主線的其他呼叫者（灰色小字）。
- 用詞寫全名：「LibreOffice 下載」而不是「LO 下載」。

### 3.3 對齊讓線變直
- 下一層的服務卡片**放在上一層呼叫它的卡片正下方（同一欄）**，線就是直的。
- 繞路一律走卡片之間的**欄間空隙**（gap 中線），並避開已被其他線使用的空隙（先查清楚哪個 gap 已被用）。
- 上一層卡片底下若有子卡（例如資料目錄），控制器的線要從**側邊空隙**繞過子卡。

### 3.4 跨層的線：總表從原方塊拉、單層圖用替身
- **總表（所有層一起）**：跨層線一律**從原本的方塊拉出來**，不要另做替身方塊（使用者會問「為何不從原本的拉」）。
  實作上把線拆兩段：A 段（只在總表）從原方塊到下一層區塊頂端；B 段（兩種視圖共用）從區塊頂端進入目標卡片。
- **單層圖**：上層方塊不在頁面上，用「來自 L1：xxx」替身方塊（放在同欄位置、底邊對齊 B 段起點），替身的 `data-id` 與原方塊相同，點擊高亮才會連動。
- 單層圖獨有的替身與其線，產生後從共用輸出中切出（`STANDALONE_ONLY`），總表獨有的線也切出（`COMBINED_ONLY`），避免兩邊混用。之後若在該層前面插入新元素（例如區塊外框），記得把這些索引一起位移。

### 3.5 下游出口與外部依賴
- 每層底部畫往下一層的 **stub（灰色虛線方塊）**：例如「L3 處理器」「L3 儲存」「L3 Office 引擎」「共用指令表（src/Shared）」。
- 沒有下一層呼叫但有資料來源的節點，連到它的資料來源 stub，不要標「終點」。
- 最底層（L3）的外部依賴放在**使用者方塊正下方**，用該層顏色畫箭頭連過去；不要把外部依賴集中成一排沒有箭頭的清單（使用者會問「為何都沒有箭頭」）。

### 3.6 L4 自動版面（檔案圖）
手排在 L4 不可行，用分層圖演算法（Sugiyama 式），每個模組一張面板：
1. **循環合併**：Tarjan SCC；互相引用的檔案合成一個紅虛線群組（標「⚠ 互相引用（N 個）」），群組內格狀排列。
2. **分層**：最長路徑，呼叫者在上、被引用的在下。
3. **跨多層的線**：每經過一層插一個看不見的中繼點（寬 10、高 0），讓長線有自己的通道，不會穿過方塊。
4. **層內順序**：重心法上下來回掃 5 次減少交叉。
5. **連接埠（防箭頭重疊）**：每條線在方塊上／下邊有**自己的接點，間隔 ≥ 16px**，依對方位置左右排序；接點放不下時**把方塊加寬**（寬度 ≥ (接點數−1)×16＋24）。
6. **通道（防橫線重疊）**：每個層間空隙中，每條需要轉彎的線分到**唯一的高度**，間隔 8px，**不要用取餘數循環重用**；空隙高度＝上下留白 14×2＋8×(線數−1)。排序：往右轉的線依起點 x 由大到小、往左轉的依起點 x 由小到大，同方向的線就不會互相交叉。上下接點同 x 的線不佔通道。
7. **路徑**：起點往下 → 在通道裡水平 → 往下進入目標；只在層間空隙轉彎。
8. **面板排版**：先算每張面板的自然寬度，再用 first-fit decreasing 裝進固定總寬的列中，列內恢復原順序、剩餘寬度平均分給面板；面板高度在畫完後量出來，不要事先估。
9. 面板頁尾寫「另引用其他模組：…」與循環警告（對應待辦編號）。

## 4. 顏色規範（最重要，必須全圖一致）

**規則：線的顏色＝發出呼叫的那一方的顏色；方塊邊框＝它發出的線的顏色。**

| 對象 | 顏色 |
|---|---|
| L0 方塊與 L0 發出的線 | 藍 `#2e90fa`（入口方塊淡藍底） |
| L1 共用畫面狀態、資料目錄、無畫面、版面表，以及它們發出的線 | 綠 `#12b76a` |
| L1 個別 renderer（需要分辨是誰拉的線時） | 同一色系的深淺：例 Native Dashboard 深綠 `#05603a`、Native 進度視窗青綠 `#0e9384`。**不要用其他層的顏色**（例如藍色會和 L0 混淆） |
| L2 方塊與 L2 發出的線（含往 L3） | 橘 `#dc6803`（卡片淡橘底；模組卡用較淡的 `#fdb022` 邊） |
| L3 方塊與 L3 發出的線（含往外部依賴） | 紫 `#7a5af8` |
| L4 面板、檔案方塊與檔案間的線 | 洋紅 `#c11574`（面板淡底 `#fdf2fa`、線 `#f670c7`） |
| 下層 stub、外部依賴 | 灰虛線 `#98a2b3` |
| 例外：未發佈／保留的元件與其線 | 灰虛線 |
| 例外：跳層違規、循環群組 | 紅虛線 `#d92d20`，並寫出檔案:行號或待辦編號 |

- 不要出現「有些依上游、有些依下游」的混用；畫完用程式掃一遍每條 edge 的 stroke 顏色，確認符合規則（見 §7）。
- 圖底部寫一行線色規則說明。

## 5. 互動與頁面（HTML 範本）

- 每個節點 `<g class="node" data-id=... data-search=...>`，每條線 `<g class="edge" data-src data-dst data-variant>`；跨兩段的線兩段都帶相同 src/dst，點擊時一起高亮。L4 節點 id 用 `面板id:檔名`。
- 功能：點方塊標出它所有連線（其餘變淡）、搜尋框、Reset、變體切換（如「全部路徑／MSIX 安裝版／--deploy 部署」）、「隱藏未發佈」切換（`.unshipped`）。
- **深色／淺色切換**：按鈕＋`html[data-theme]`；頁面框架用 CSS 變數色，圖面用 `filter: invert(.9) hue-rotate(180deg) saturate(1.15)` 讓語意色相保留；預設跟系統 `prefers-color-scheme`，選擇存 localStorage（try/catch 包起來）。
- 不要有 hover tooltip。
- **縮放行為**（使用者逐條要求過）：
  - 100% 時圖寬＝視窗寬（用 CSS `width:100%`，不要寫死 px），**沒有橫向捲軸**（`overflow-x:hidden`）。
  - 瀏覽器放大（Ctrl+）時**方塊文字跟著放大**：以載入時的 `devicePixelRatio` 當 100%，`z = dpr/base`；z≠1 時把圖寬設成 `min(圖原寬, clientWidth*z)` px，允許橫捲。
  - **標題列不放大**：`header.style.zoom = 1/z`。
  - 只有一個捲動區：body 用 flex column，標題列自然高度，圖區 `flex:1; overflow:auto`，避免出現兩條垂直捲軸。
  - 工具列固定一行（放不下時橫向捲動），統計與說明收進「說明」按鈕切換。

## 6. 產生器結構（可重跑、可維護）

```
Claude outputs/
├─ README.md                 ← 每個檔案是什麼（表格）
├─ 架構圖/
│   ├─ 總表.html              ← 所有層一起
│   ├─ L0_入口.html … L4_模組內部.html
├─ 待辦問題清單.md
├─ _產生器/
│   ├─ layers.py             ← 主程式：共用繪圖函式、L0、L1、各視圖匯出
│   ├─ l2_block.py           ← 每層一個 block 檔，依序 exec（l2 → l3 → l4）
│   ├─ l3_block.py
│   ├─ l4_block.py           ← 自動版面
│   ├─ l4.json ＋ 掃描腳本    ← L4 資料（在使用者電腦上產生）
│   ├─ files_map.py
│   ├─ *_template.html       ← 頁面範本（__SVG__／__META__ 佔位）
│   └─ svg/                  ← 同內容純 SVG
└─ _舊版（可刪）/             ← 被取代的東西搬進來，不要亂丟在根目錄
```

- 用 Python 產 SVG 字串清單 `o`，記錄每層在 `o` 裡的起訖索引（`L1_AT`、`L1_END`、`L2_AT`…），單層圖用切片＋該層替身＋頁尾組合；總表用全部。
- 每層包在 `<g transform="translate(0, 該層頂端)">`，外層再一個 `translate(左側標題欄寬, 0)`；區塊高度在內容畫完後才知道時，先記住外框在 `o` 中的位置，畫完再插入；總高 `H` 最後回填 `o[0]`。切片時注意 `<g>` 開關要成對（產生後用 `xml.dom.minidom.parse` 驗證每個 svg）。
- `path(points, …, color, dashed, arrow=True)`：A 段用 `arrow=False`。
- 方塊函式內 assert 文字最後一行不超過方塊高度；區塊總高度也 assert，超過就調整常數而不是讓它溢出；`max()` 前先處理空清單。
- 改圖只改 `_產生器/`，重跑覆寫 `架構圖/`；舊檔名改名時把舊檔搬進 `_舊版（可刪）/` 並更新 README。
- 刪除檔案需要權限時，改為搬到 `_舊版（可刪）/`，請使用者自己刪。
- 雲端保留一份來源，改完後把變更的檔案寫回使用者資料夾（只寫有變的檔）。

## 7. 驗證（每次改完都要做，不要等使用者問「你要不要去確認一下」）

1. 重跑產生器，所有 assert 通過；所有 svg 能被 XML parser 解析。
2. 用 Playwright（cloud 內建 Chromium）開每個 HTML，收集 `pageerror`，必須為空。
3. **自動幾何檢查**（在頁面內用 JS 跑，每項都必須是 0）：
   - **文字溢出**：每個方塊內 `<text>` 的 bbox 不超出方塊 rect。
   - **線穿過方塊**：沿每條 path 以 `getPointAtLength` 每 3px 取點，落在非起訖方塊內（內縮 2px）即違規。
   - **方塊超出面板**、**方塊互相重疊**（bbox 比對，容差 1px）。
   - **箭頭太近**：解析每條 path 的 `d` 取終點，任兩條線終點 y 差 < 3 且 x 差 < 14 即違規（箭頭會疊在一起）。
   - **平行線段重疊**：把每條 path 拆成水平／垂直線段，不同線的同向線段距離 < 4px 且重疊長度 > 2px 即違規（看起來像同一條線）。
4. **人工截圖**：1556 寬整頁分段截圖；再對**最密的目標方塊放大截圖**（`device_scale_factor=2`、裁切該方塊上方約 260px 範圍），確認箭頭與通道清楚分開。數字全為 0 也要看圖。
5. 點幾個關鍵節點截圖確認高亮連動（含跨層兩段線）；切深色再截一張；模擬放大（改 dpr）確認文字變大、標題列不變大、只有一條捲軸。
6. **顏色稽核**：列出每條 edge 的 stroke 與 src→dst，確認符合 §4（例：藍色只能出現在 src 為 L0 節點的線）。
7. **事實稽核**：圖上每個檔名在 repo 中存在（逐一 `[ -f ]`）；跨層線抽查行號。
8. Windows 實際字型（Consolas 約 0.55em/字）比雲端字型窄、但使用者截圖會縮放；寬度要留餘裕。

## 8. 待辦問題清單（畫圖時同步維護）

畫圖過程中發現的問題全部寫進 `Claude outputs/待辦問題清單.md`，不要只講在對話裡：

- 開頭註明整理日期與基準（分支、HEAD commit、是否已 push）。
- 依區塊分組：A 分支與 PR、B L0、C L1、D L2、E L3／L4 與其他；最後列「已處理（供對照）」。
- 每項欄位：編號、優先（🔴 先處理／🟡 排得進來就做／⚪ 記錄即可）、問題、位置（檔案:行號）、建議。
- 圖上的紅虛線、循環群組、灰色「也被」註記、孤兒節點都要能對應到清單編號（在方塊說明寫「見待辦 D2」）。
- 發現先前描述錯了（例如把註解當呼叫），同時改圖和清單。

常見值得找的問題類型：跳層呼叫、同一流程在兩處重複（例如 CLI 與 Presentation 各寫一份執行流程）、同一判斷寫三份（「要開哪個 UI」）、入口層直接操作任務紀錄或用 `Sleep` 對時序做假設、在地化等橫切模組直接讀儲存層、正式程式已無呼叫者只剩測試在用的死碼、參數用空白 `Join` 導致路徑被拆開、上層直接引用下層的選項／列舉型別、處理器與引擎互相引用、門面與 Store 互相引用、Model 反向引用 Pipeline。

## 9. 與使用者互動的節奏

- 每完成一層：一兩句說明這層的版面與發現，指出檔案位置，問題清單另檔。
- 使用者對顏色、版面提出「為何這樣」時，先**盤點現況**（用表格列出現在每種線／方塊是什麼顏色、依什麼規則），承認不一致，再提 1~2 個方案並給建議。
- 使用者說「ok」就照建議做，做完截圖自查再回報。
- 回覆用使用者的語言（繁體中文），簡短，不貼大段程式碼。
